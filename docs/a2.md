## 原理与关键实现详解

对应 [官方 A2](https://github.com/stanford-cs336/assignment2-systems)。先读 A1；本章核心代码是 [flash.py](../src/cs336_systems/flash.py)、[flash_triton.py](../src/cs336_systems/flash_triton.py)、[distributed.py](../src/cs336_systems/distributed.py)。

## 1. A2 优化的是哪一部分

A1 定义模型计算和优化目标，A2 在尽量保持相同数学计算的前提下减少耗时和内存。加速不是另换一个更小的模型，再把变快全部归功于内核。必须先固定输入形状、dtype、因果性和硬件环境，再验证输出与梯度，最后测速度。

一个训练 step 可以拆成：取数据、主机到设备传输、forward、loss、backward、梯度通信、optimizer、同步与日志。只测 attention forward 不代表整个训练同比例加速。若 attention 只占 30% 耗时，即便完全消除它，总加速也最多约 1/0.7=1.43 倍，这就是 Amdahl 定律的直观含义。

## 2. GPU 上怎样计时才有意义

CUDA 调用通常异步返回。Python 计时若不等 GPU 执行完，可能测到的只是提交任务耗时。仓库 [benchmark_model.py](../scripts/benchmark_model.py) 与 [benchmark_attention.py](../scripts/benchmark_attention.py) 提供预热、同步计时与记录。

```python
# 等价计时流程
for _ in range(warmup): operation()
torch.cuda.synchronize()
start.record()
operation()
end.record()
end.synchronize()
milliseconds = start.elapsed_time(end)
```

预热用于触发 CUDA 上下文、Triton JIT、缓存和可能的编译；首次编译耗时应单独报告。重复多次看中位数与离散程度。共享 GPU 上其他任务会影响时延与频率，单个数值不构成稳定加速结论。

`memory_allocated` 是当前张量分配；`memory_reserved` 包括 PyTorch 缓存池；`nvidia-smi` 的进程占用还可能包含上下文、库工作区。三个数不应被当成同一个指标。每 step 重置峰值时，训练器的局部峰值与外部低频采样也可能不同。

Profiler 的作用是定位瓶颈：很多小 kernel 可能受 launch 开销影响；大型 matmul 可能受计算吞吐影响；大规模读写但很少计算的 kernel 可能受带宽限制。算术强度=FLOPs/从内存搬运的字节数，帮助判断优化是该减少访存还是提高计算利用率。

## 3. 朴素注意力为何浪费存储

对每个头，Q/K/V 为 `[T,dh]`，注意力分数与概率为 `[T,T]`。T 从 1024 增到 4096 时，Q 的元素数增 4 倍，P 的元素数增 16 倍。多个 batch、头和层让 T² 激活成为显存大户。

FlashAttention 并没有把 dense attention 的数学计算量从平方变成线性。它把 Q/K/V 分块放到更快的片上存储中，融合 softmax 与乘 V，避免把完整分数矩阵写回显存，反向再重算需要的概率。

## 4. 在线 softmax：最关键的推导

对一个 query 行，我们需要 `sum exp(sⱼ)vⱼ / sum exp(sⱼ)`。分块后不能直接把每块 softmax 输出相加，因为每块的分母不同。

维护三项：已经看过分数的最大值 m、相对 m 的指数和 l，以及未归一化加权和 a。新块分数为 S，新最大值 `m'=max(m,max(S))`。令 `α=exp(m-m')`，则旧累计项都要乘 α，以统一到新的指数基准：

`l'=αl+sum exp(S-m')`

`a'=αa+exp(S-m')V_block`

结束后 `O=a/l`，保存 `LSE=m+log(l)`。这是稳定在线归一化的完整原因。

```python
# flash.py 实际核心节选
m_new = torch.maximum(m, scores.max(-1).values)
correction = (m - m_new).exp()
p = (scores - m_new[..., None]).exp()
l = correction * l + p.sum(-1)
acc = correction[..., None] * acc + p @ vj
m = m_new
```

手算例子：第一块分数只有 0，V=2，则 m=0,l=1,a=2；第二块分数 log2，V=5，新 m=log2，旧项乘 1/2，得到 l=1.5，a=6，输出 4。直接拼接两块 softmax 的结果 2+5=7 显然不对。

因果性依旧需要 j≤i。tile 最后一块常常不足完整尺寸，load/store 必须 mask 掉越界位置；不存在的 key 应贡献零概率。不要让一行的所有有效 key 都被错误屏蔽，否则会遇到 `-inf-(-inf)` 的 NaN。

## 5. 为什么 backward 可以重算

设 `O=PV`，上游梯度为 dO。基本关系：

`dV=PᵀdO`，`dP=dOVᵀ`。

softmax 的行梯度为 `dS=P⊙(dP-sum(P⊙dP))`。又因为 `sum(P⊙dP)=sum(O⊙dO)`，可以先算每一行的标量 `delta`。前向保存了 LSE，反向按 tile 重算：

`P_tile=exp(Q_tile K_tileᵀ/√dh - LSE)`。

```python
delta = (do.float() * out.float()).sum(-1)
p = (scores - lse[..., i:i+32, None]).exp()
ds = p * ((doi @ vj.transpose(-1,-2)) - delta[..., i:i+32,None])
dq += ds @ kj / math.sqrt(dh)
dk += ds.transpose(-1,-2) @ qi / math.sqrt(dh)
dv += p.transpose(-1,-2) @ doi
```

输出 O 与 LSE 的额外存储是 O(Tdh+T)，没有保存完整 P。代价是 backward 重算分数，这是一种用更多计算减少显存流量的选择。

## 6. 从 Python 分块到 Triton kernel

PyTorch 分块版便于推导和对照，但 Python 循环会发出很多 kernel。Triton 将 tile 内的 load、dot、max、exp、sum、store 放到一个 GPU program 中。

`program_id` 决定当前处理哪个 query tile、哪个 batch/head；`tl.arange` 生成 tile 内偏移；load 的 mask 保护不规则长度；`tl.dot` 执行矩阵乘；在线 softmax 的累计量通常保留 FP32。program 间没有全局同步，设计时不能假设另一个 tile 已经完成。

仓库 backward 拆为 delta、dQ、dK/dV 等 kernel。dQ 的一个 program 负责自己的 query tile；dK/dV 的一个 program 负责自己的 key tile。通过改变遍历方向避免多个 program 同时写同一梯度地址，从而减少原子加法与竞态。

`num_warps`、block size、`num_stages` 控制线程组织与流水线资源，并不保证越大越快。上一轮 dh=128 在默认流水级数下要求 102,400B shared memory，超过该设备每 block 可用 101,376B；本仓库对 dh=128 使用 `num_stages=1` 后重新通过数值对照。这说明“GPU 有很多总显存”不能解决“单 block 共享内存超限”。

误差判据通常是 `|a-b|≤atol+rtol|b|`，BF16 合理容差大于 FP32。必须事先定义容差并解释误差来源，不能遇到失败就逐次放宽，直到“通过”。本次数值对照见results/a2/flash-numerics.json，不能用单个最大绝对误差判断所有相对误差断言。

PyTorch SDPA 应显式使用 `[B,H,T,dh]`；若只传三维输入，可能选择不同后端。比较自写 Flash 与官方 Flash 时，用 `--sdpa-backend flash` 强制后端，确认没有 fallback 到 math。每个实现还应使用相同预热、重复次数、形状与 dtype。

## 8. DDP：多卡为什么要同步梯度

每个 rank 持有完整模型，读取不同数据，得到本地平均梯度 gᵣ。如果各 rank batch 一样大，目标全局梯度是 `sum(gᵣ)/world_size`。同步后各 rank 用相同优化器状态更新，模型继续保持一致。

NaiveDDP 在 backward 后逐参数 all-reduce，容易受大量通信调用延迟影响。FlatDDP 把梯度拼成较大缓冲区再 all-reduce，减少调用次数，但通常要等 backward 完成。OverlapDDP 在参数梯度 ready hook 中发起异步 all-reduce，与剩余反向计算重叠；optimizer.step 前必须等待全部通信完成。

仓库 [distributed.py](../src/cs336_systems/distributed.py) 实现这三条路径。`async_op=True` 不等于结果已可读；忘记 wait 会在未完成通信的梯度上更新参数，产生时序相关错误。

梯度累积与通信也有关系：每个 microbatch 都同步最简单但开销大；真正生产系统可以在前几个 microbatch 采用 no_sync，最后再同步。本教学实现的接口语义以源码为准，不默认宣称有完整生产框架的所有优化。

## 9. ZeRO-1 与 FSDP：分片到底分了什么

FP32 Adam 的常见静态存储是参数4N、梯度4N、m4N、v4N 字节。DDP 每卡都承担约16N。

ZeRO-1 只分优化器状态：每个参数指定一个 owner rank，该 rank 保存 m/v 并更新，然后广播新参数。每卡仍有完整参数与梯度，近似变成 `8N+8N/P`。仓库 `ShardedOptimizer` 用参数顺序轮转指定 owner，保存 state 时记录 world size 和映射，恢复需要检查一致性。

FSDP 连参数和梯度也分片：

1. 平时保存 FP32 参数 shard。
2. 当前层 forward 前 all-gather 得到完整参数，用计算 dtype 执行。
3. 用完释放临时全参数缓冲区。
4. backward 需要时再次 gather、重算本层梯度。
5. reduce-scatter 把梯度求和并送回对应 shard；本地优化器更新 shard。

理论静态项可接近16N/P，但还需当前层全参数、激活、通信缓冲和未分片参数。仓库对 Linear/Embedding 使用自定义 autograd 分片路径，norm 参数保留复制；它是教学实现，不等价于生产 FSDP 对预取、共享权重、弹性恢复等所有功能的支持。

## 10. 单卡服务器的实验边界与练习

单张 PRO 6000 可以真实验证 Triton、attention 前后向、模型吞吐与显存；CPU 多进程可以检查通信语义和分片恢复。把两个进程放在同一张 GPU 上不等于拥有两张独立 GPU，也不能据此推断多卡扩展效率。

正式 A1 基线保持现有数学实现；A2 优化实验建立独立对照目录，记录 token 数、loss、峰值内存与 walltime。大型官方配置可能静态状态就超过 40–50GiB，不应因为小模型能跑就全部无条件启动。

练习：写出 online softmax 的三块手算结果；分别估算 T 翻倍的 FLOPs 与存储；给 Flash backward 注入非均匀上游梯度；画出两个 rank 的 overlap 时间线；解释为何 ZeRO-1 仍保存完整梯度；说明 FSDP 中在 layer backward 后释放何种缓冲才不会破坏后续反向。
